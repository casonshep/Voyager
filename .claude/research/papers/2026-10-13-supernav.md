# SuperNav

## What it is

A navigation harness around an unmodified multimodal LLM (GPT-5.6 Terra, GPT-6 Astra). The model
interprets requests and scenes and picks destinations by pointing at image coordinates; tools
execute motion; Markdown "Navigation Skills" give procedural guidance on demand. No
navigation-specific fine-tuning.

## What it says

- **Results** (Table 1): single-object 78.0% SR vs 34.0% for the best baseline; demand-driven
  59.5% vs 37.5%; HM3D-OVON 73.3% SR at 1 m without OVON training.
- **Ablation** (Table 3, OVON, 120 episodes, SR at 0.25 m / 1 m): without Skills 35.0 / 54.2;
  without the agent-oriented Tool design 52.5 / 65.8; without both 31.7 / 54.2; full 68.3 / 73.3.
  The Markdown guidance is worth more than the interface. Swapping the model to GPT-6 Astra
  (medium) with the harness fixed raised SR to 71.7 / 79.2.
- **Skills** (Sec 3.3): "Each Skill is a Markdown package describing its applicable situations,
  evidence to inspect, recommended steps, and linked references." Loaded on demand by name and
  description. Skills "neither add environment capabilities nor programmatically enforce action
  sequences." Guidance covers three recurring decisions: where to search, how to recover, when to
  finish.
- **Tools** (Sec 3.2): "inputs easy for the MLLM to specify and returns useful for the next
  decision." A motion tool returns the new four-view observation, execution status and concise
  diagnostics, so no separate observe call after each move.
- **Context** (Sec 3.1): goal records hold pending and completed items; text history keeps
  inspected areas, candidate clues and failed attempts; pruning is media-only (old images dropped,
  text kept, paths retained so the model can re-request an image).
- **Termination**: the model declares achieved or blocked; scoring is separate. A "blocked" close
  is refused in the skill rules unless every alternative was tried ("evidence, not likelihood").

## What the code contains

`skills/global-navigation/SKILL.md`: frontmatter, rules with stable IDs (GN-OBS-002,
GN-MOVE-001, GN-TERM-010) using MUST / SHOULD / MAY, and a "load the needed rules" table that
says *when* to read each reference (`spatial-memory.md` before the first junction,
`exploration-and-return.md` before leaving an area, `recovery-and-stop.md` at the first stall).
Recovery is a fixed ladder: inspect views, enter an unfamiliar room, try an unentered sibling, one
bounded adjustment, return to an older frontier. Runtime is Codex CLI over MCP tools.

## What applies to this project

- **Skills as Markdown for the builder and decomposer, loaded on demand.** Maps to: the builder's
  hand-written `CONTRACT` (`voyager/tree/builder.py:71-227`), which never updates from experience.
  Proposal: per-family skill files (find-X, acquire-X, craft-X, place-X) maintained by the
  post-goal review (R4), with rule IDs and a "read this when" table; the builder loads only the
  relevant one. Jev never sees them.
- **Every action returns the next observation.** Maps to: action records in `agentLoop.js`.
  Proposal: attach the post-action observation delta (view, horizon, inventory) to each record so
  `progress` is judged on deltas (R2, R5).
- **find-X as search / recheck / recover / complete.** Maps to: `locate` nodes and explore
  primitives. Proposal: the recovery ladder in code replaces the least-recently-used movement
  fallback; "complete" is an evidence gate (target visible or held).
- **Census before decision.** Maps to: `observe.js` horizon. Proposal: label each direction
  traversed / inspected / new rather than passing raw offsets (R5, R6).
- **Blocked ledger before escalating.** Maps to: the `completable` checkpoint. Proposal: require
  that each applicable menu action was tried with its outcome before firing the builder (R3).

## What does not apply

Image-point interface, depth back-projection, navmesh and learned motion backends, the robot.
